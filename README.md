# Endpoint Explorer

**Understand how your trial endpoint is behaving.**

A product-management prototype exploring how a CNS / mental-health clinical trial
team might inspect the behavior of a primary endpoint *during* a study — before
database lock, before formal analysis — to answer one question:

> Is this endpoint giving us a clean, interpretable signal, and what might be
> affecting it?

All data is **synthetic / demo data**, generated locally in the browser. This is
not a clinical decision tool, a diagnostic tool, or a validated statistical
product.

---

## The product problem

Trial teams watch an endpoint accumulate for months. Standard tooling shows them
a mean-over-time line and a table of dropouts. That hides the things that
actually determine whether the endpoint will support a decision:

- **When** did the arms start behaving differently — early, late, or not at all?
- Is a large **placebo response** compressing the visible separation?
- Is **missing data** accumulating unevenly between arms?
- Is the mean masking a **bimodal** participant-level response?
- Would a different **endpoint definition** (raw / change / % change) make the
  signal easier or harder to see?

Endpoint Explorer is a single screen that walks through those questions in order,
each section answering exactly one.

## Target user

- **Primary:** clinical scientists, biostatisticians, and study-team leads on a
  sponsor or CRO trial team, reviewing a blinded or unblinded endpoint mid-study.
- **Secondary:** product and data teams building trial-analytics tooling who need
  a concrete reference for what "endpoint quality" inspection could look like.

## Key product decisions

1. **One question per section.** Every block has an eyebrow line phrased as the
   user's question ("Are we losing participants?") and a single visual that
   answers it. No generic "metrics" grid.
2. **Observations, not conclusions.** The "Endpoint health panel" is generated by
   deterministic rules over the dataset (separation threshold crossing, placebo
   % improvement, completion delta, SD ratio). The language is templated and
   descriptive — it never says a result is significant, meaningful, or clinical.
3. **Descriptive statistics only.** Variability bands are ±1.96 SEM of the visit
   mean, labeled as such. There is no hypothesis test, p-value, or model
   anywhere in the app, by design.
4. **Aggregate → individual is a first-class path.** The participant table opens
   a side panel with that person's own trajectory against the arm mean, to make
   the "the average hides variation" point tangible.
5. **Endpoint definition is a lens, not a ranking.** The compare view switches
   raw / change / % change and shows how the same data looks different. It
   explicitly does not claim one definition is better.
6. **Restrained visual system.** Off-white canvas, one serif-free typeface, two
   arm colors (teal / ochre), hairline borders, no gradients, no cards-in-cards.
   Charts dominate; chrome recedes.
7. **Three studies with different stories.** AURORA-201 (MDD) has a modest,
   slow-emerging separation; CALM-102 (GAD) has almost no separation and a large
   early placebo response; FOCUS-301 (ADHD) has a strong separation with rising
   variability. Switching studies shows the tool reacting, not just re-skinning.

## What the prototype demonstrates

- A believable clinical-research review workflow on a single, scannable page.
- Deterministic, rules-based "what should I look at?" guidance that stays inside
  what synthetic data can support.
- Interactions that change what you notice: mean vs change toggle, variability
  band, placebo threshold/window explorer, retention by arm, endpoint-definition
  lens, and per-participant drill-down.
- Synthetic longitudinal data (~120–130 participants/study) with baseline
  variation, gradual treatment improvement, early placebo improvement, correlated
  participant-level noise that widens over time, and realistic differential
  dropout.

## Limitations

- **Synthetic data only.** Participants, sites, scores, and studies are generated
  by a seeded RNG (`lib/rng.ts`, `lib/synth.ts`). Nothing is derived from real
  patients, and the generative model is a simplification.
- **No inference.** Bands are ±1.96 SEM of the mean for orientation only; they
  are not confidence intervals for a treatment effect and support no
  significance claim.
- **Thresholds are illustrative.** The 10/20/30% placebo-improvement cut points
  and the 1.5-point separation trigger are for exploration, not validated
  responder criteria.
- **Single primary endpoint per study.** No multiplicity, no secondary
  endpoints, no missing-data imputation strategy modeled.
- **Not blinded-review-safe.** A real mid-study tool would need to respect
  blinding rules and access controls; this prototype ignores them.

## What I would validate next

- **Which endpoint-quality signals are most useful to trial teams?** Is
  separation-onset the thing they want first, or is it missingness / placebo
  response? Does the ranking differ by role (biostat vs medical vs ops)?
- **When do researchers need participant-level vs aggregate views?** Is the
  drill-down a daily tool or only for investigating an anomaly someone already
  flagged?
- **How should placebo-response patterns be surfaced without over-interpreting
  them?** The current framing ("X% of placebo improved ≥20%") is deliberately
  flat — is that useful, or does it need context (historical placebo rates,
  by-site breakdown) to be actionable?
- **What information actually changes a trial team's next decision?** Enrollment
  pace, protocol amendment, site intervention, sample-size re-estimation — which
  of these does an endpoint-behavior view realistically feed, and what would it
  need to show to be trusted there?
- **Does the endpoint-definition lens help or distract?** Useful for aligning a
  team on what they're looking at, or a source of false "we could just redefine
  it" optimism?
- **Cadence and diffing.** Teams review repeatedly — would a "what changed since
  last review" view matter more than any single snapshot?

## Tech

- **Next.js 14** (App Router) + **TypeScript**
- **Tailwind CSS** for styling
- **Recharts** for charts, **lucide-react** for icons
- No backend. Data is generated client-side and memoized per study.
- Static export (`output: "export"`) — deployable to Vercel, GitHub Pages, or any
  static host.

### Run locally

```bash
npm install
npm run dev
# http://localhost:3000
```

### Build

```bash
npm run build      # produces ./out (static export)
npx serve out      # preview the production build
```

### Deploy

**Vercel** — import the repo; framework preset "Next.js"; no environment
variables needed.

**GitHub Pages** — the included workflow
(`.github/workflows/deploy.yml`) builds the static export and publishes it on
every push to `main`. Enable it under **Settings → Pages → Source: GitHub
Actions**. The workflow sets `NEXT_PUBLIC_BASE_PATH` to the repo name so assets
resolve under `https://<user>.github.io/<repo>/`.

### Project structure

```
app/

  page.tsx              single page; owns study / loading / drawer state
lib/

  types.ts              data model
  synth.ts              synthetic longitudinal dataset generator (seeded)
  analysis.ts           all derived metrics — deterministic, descriptive only
  format.ts             number formatting
```
